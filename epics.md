# TicketTrade (NSBM Marketplace) - Epic Breakdown

## Overview

This document provides the complete epic and story breakdown for TicketTrade (NSBM Marketplace), decomposing the requirements from the PRD, UX Design, and Architecture into implementable stories. The product is a campus-only peer-to-peer marketplace for NSBM Green University students, built on PHP 8 + MySQL + Bootstrap 5 with a Layered Modular Monolith architecture (Bootstrap → FrontController → Action → Service → Model → PDO).

### NonFunctional Requirements

Because brand-new listings always enter pending and flagged relisted content stays under admin re-check, the platform does NOT rely on the intermediary safe-harbor "no proactive curation" argument. **Action:** the compliance basis is notice-and-takedown plus the tamper-evident audit trail (FR-ADM-006); document the moderation policy in the project report. [ASSUMPTION-004] NSBM IT policy aligns
- **NFR-CMP-002:** PDPA No. 9 of 2022 — substantive provisions not yet in force as of Aug 2026. **Action:** Minimal personal data collected (name, student ID, email, optional WhatsApp); no sensitive data. [ASSUMPTION-002] No PDPA compliance work needed for MVP

- **NFR-CMP-004:** NSBM IT policy for student projects — not found in public sources. **Action:** Document hosting, data retention, and liability in project report. [ASSUMPTION-001] Faculty sponsor approves deployment

- **NFR-REL-001:** Idempotent ticket redemption (re-redeeming returns current state, not error); a correct-code resubmission is idempotent and does NOT consume a rate-limit attempt
- **NFR-REL-002:** Idempotent cron job (re-running same day produces no duplicate effects); **staging replay: `TRUNCATE cron_log; php jobs/ticket_expiry.php` = identical result** for ticket expiry; documented exception: the 24h auto-approval sweep is intentionally non-idempotent across days (see NFR-OPS-003)
- **NFR-REL-003:** Database foreign keys with `ON DELETE CASCADE` / `SET NULL` / `RESTRICT` where appropriate
- **NFR-REL-004:** Atomic UPDATE for ticket redemption (no explicit transaction needed)
- **NFR-REL-005:** Points ledger uniqueness via `UNIQUE KEY uniq_event (event_uuid)` — one row per points event, covering retries and closing the duplicate-NULL hole of composite nullable keys
- **NFR-REL-006:** **FK `tickets.listing_id` ON DELETE RESTRICT** — seller cannot delete listing with active tickets
- **NFR-SEC-001:** Passwords hashed with bcrypt (cost ≥ 12) — never plaintext
- **NFR-SEC-002:** All SQL via prepared statements (PDO) — no concatenation
- **NFR-SEC-003:** CSRF tokens on all state-changing forms (synchronizer token pattern, `hash_equals()` validation)
- **NFR-SEC-004:** File uploads: 4-layer validation (finfo MIME, getimagesize dimensions ≤4000px/5MB, magic bytes, GD re-encode to WebP); **max chunk 2MB, total 5MB**; store outside webroot; serve via PHP proxy (thumbnails public, full-size images auth-checked)
- **NFR-SEC-005:** Input validation: server-side + client-side; XSS prevention via `htmlspecialchars` on output
- **NFR-SEC-006:** Session cookies: `HttpOnly`, `Secure` (in prod), `SameSite=Strict`, `use_strict_mode=1`, `sid_length=48`
- **NFR-SEC-007:** Rate limits: login 5/5min per IP, purchase 10/hr per user, listing_create 20/hr/user, points 150/day/user, **redemption 5/hr/ticket**; **per-user limits (not just IP)**
- **NFR-SEC-008:** Security headers: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, CSP with CDN allowances
- **NFR-SEC-009:** **WhatsApp number validation**: server regex `^(\+94|0)7[0-9]{8}$` (Sri Lankan mobile)
- **NFR-SEC-010:** **Admin re-auth**: password confirmation required for ban, promote, delete, bulk actions
- **NFR-USE-001:** Responsive: mobile-first, breakpoints at 576px, 768px, 992px, 1200px (Bootstrap 5 grid)
- **NFR-USE-002:** Keyboard navigable: all modals trap focus, ESC closes, ARIA labels on interactive elements; **focus returns to trigger on close**
- **NFR-USE-003:** Color contrast: WCAG AA minimum (4.5:1 text, 3:1 UI elements) — verified in test plan via axe-core or manual audit

### Additional Requirements

- **Starter template:** No starter template is specified; build substrate is a hand-rolled PHP 8.4 + MySQL 8.4 + Bootstrap 5 `Layered Modular Monolith` (Bootstrap → FrontController → Action → Service → Model → PDO), with webroot at `public/`, `src/` outside webroot, hand-rolled route list, no ORM, no regex routing, no framework (AD-1..AD-4).
- **Bounded contexts:** `Auth`, `Listing`, `Ticket`, `Points`, `User`, `Category`, `Report`, `Admin`, `Cron`, plus `src/Support/` cross-cutting; a Context never imports another Context's Model — inter-context work goes through a Service (AD-2).
- **PDO singleton:** `Support\Db::pdo()` is the single request-scoped connection; all SQL is `prepare` + `execute([...])`, no string concatenation, no ORM (AD-5).
- **Migrations:** `migrations/NNN_*.sql` files + `migrations/.applied` set; `php migrate.php` runs missing files in lexical order inside a single transaction per file; forward-only (AD-6).
- **Inventory invariant:** `quantity_sold` increments ONLY inside the ticket-creation transaction; redemption is a no-op for stock; expiry and Force Expire decrement (AD-7).
- **Ticket code format:** `TK-` + base62(`random_bytes(16)`)[:22] (≥125 bits entropy); internal IDs are `BIGINT UNSIGNED AUTO_INCREMENT`; `points_log.event_uuid` is UUID v7 via `ramsey/uuid`; generation runs in a retry loop on `UNIQUE` violation (max 10 attempts) (AD-8).
- **Atomic UPDATE pattern:** every state-changing ticket operation is a single `UPDATE tickets SET ... WHERE ticket_code = ? AND status = ? AND dispute_status != 'pending' AND seller_id = ?`; `rowCount() === 0` is the invalid branch; no `SELECT FOR UPDATE`, no explicit transaction (AD-9). Force Expire is the only operation allowed to override an open `dispute_status='pending'`.
- **Points engine:** every point movement writes a `points_log` row (event_uuid UUID v7, `UNIQUE uniq_event`) AND updates `users.points` + `users.tier` in the same DB transaction; tier recomputed from `config/ranks.php`; velocity check at insert time sets `users.points_frozen=TRUE`; FR-PTS-007 multiplier is new-account-only on counted transactions; pair-cap is per buyer-seller pair, not per user (AD-10).
- **Cron owns three sweeps:** `jobs/ticket_expiry.php` (hourly, file-locked via `flock()`) owns (a) ticket expiry, (b) 24h listing auto-approve, (c) 3-day dispute auto-dismiss; `jobs/daily_cron.php` (02:00 Asia/Colombo) owns leaderboard refresh, daily/weekly report generation, streak recompute, retention marking; both log to `cron_log` and are idempotent within the same wall-clock day; both are also exposed at `POST /admin/cron/<job>` behind admin re-auth (AD-11).
- **Audit log:** `audit_log` rows carry `prev_hash = SHA256(prev.prev_hash || json_encode(canonical_row))`; inserts serialize through MySQL named lock `GET_LOCK('audit_log_chain', 5)`; the chain is re-walked for the last K=1000 rows on every admin audit page render; full re-walk exposed at `POST /admin/cron/audit_reverify`; no UPDATE/DELETE on `audit_log` exists (AD-12).
- **Auth, session, CSRF, rate-limit:** session config at bootstrap; per-session synchronizer CSRF token with `hash_equals()` compare; rate limits per-user AND per-IP; a correct-code redemption resubmission is idempotent and does NOT consume a rate-limit attempt; security response headers (CSP, X-Frame-Options DENY, X-Content-Type-Options nosniff, Referrer-Policy) set by `Support\ResponseHeaders` at front-controller boot (AD-13).
- **File storage outside webroot + image proxy:** uploads in `/var/www/uploads/listings/<sha256-hash>.webp` with three WebP 80% thumbnails (200/600/1200); `Support\ImageProxy` serves by id — thumbnails (200/600) unauthenticated, full-size (1200) requires auth AND one of (seller, ticket-holder, admin); validation pipeline: `finfo` → `getimagesize` → magic bytes → GD re-encode; default 5MB/file, 2MB/chunk, 8 images/listing; Uppy.js `chunkSize` MUST be 2 MiB to match server limit (AD-14).
- **Reviews and disputes gate on ticket state:** reviews insertable only when `tickets.status IN ('redeemed','expired') AND tickets.dispute_status='none'`; disputes fileable only when `tickets.status='active' AND tickets.dispute_status='none'`; `reviews UNIQUE (ticket_id, reviewer_role)`; public seller profile shows count only, never narrative (AD-15).
- **Failure envelope:** every Action returns `['ok'=>bool,'data'=>mixed,'error'=>['code','message','fields?']]`; View renders `error.message` only via `htmlspecialchars()`; stable error codes (`E_AUTH_INVALID`, `E_LISTING_NOT_FOUND`, `E_RATE_LIMIT`, `E_CSRF`, `E_VALIDATION`, `E_TICKET_CODE_EXHAUSTED`) — UI switches on code, not on message text; unhandled exceptions render a generic 500 page (AD-16).
- **Operational envelope:** dev server `php -S localhost:8000 -t public` with `public/router.php`; `php migrate.php` for schema; `vendor/bin/phpcs --standard=PSR12 src/` for lint; composer runtime `ramsey/uuid ^4.7` only; dev `phpcs`, `phpunit`; all admin/sensitive actions write an `audit_log` row (AD-17).
- **Credentials are bcrypt-only at cost ≥ 12:** `Auth/Service/auth_service.php` is the sole caller of `password_hash()` / `password_verify()`; cost constant lives in `config/auth.php` (default 12); every `INSERT`/`UPDATE` of `users.password_hash` MUST go through this Service; a phpcs sniff `Custom\Sniffs\NoRawHash` rejects `md5(`, `sha1(`, `crypt(`, and `password_hash(` outside `Auth/Service/auth_service.php` and `Support\Crypto`; student-ID allowlist seeded with ~50 demo accounts (AD-18).
- **Admin re-auth mechanism:** sensitive admin actions require a re-auth POST that includes the current admin's `password_hash` verified against `password_verify()` within the last 300 seconds (sliding); result cached server-side in `admin_reauth` table keyed by `(user_id, session_id)`; re-auth itself rate-limited at 5/min/IP; full re-login is NOT acceptable as the only mechanism (AD-19).
- **Cohort isolation is a go/no-go gate:** MVP assumes a single cohort; no `cohort_id` column added; the team decides at S2 retro whether to add `cohort_id` in migration `013` with `DEFAULT 'cohort-1'` and `WHERE cohort_id = ?` belt across every Model — this MUST be decided before per-screen implementation work for FR-LST-005 (flyer modal) begins (AD-20).

The three promoted mockup HTML files in `mockups/` are the visual contract. The full screens are implemented in later epics; this epic only ships the static assets + tokens.

### Epic 2: Student Authentication & Profiles
A verified NSBM student can register, log in, manage their profile, and log out. Session, CSRF, rate-limit, and bcrypt-only primitives land here as `Support\` services for later epics to consume. Route guards are in place so that later epics can assume `current_user` is authenticated.

### Epic 3: Marketplace Listings & Discovery
A seller can create, edit, and manage listings through the full listing state machine (draft → pending → active / rejected / sold / removed, with the FR-LST-015 approved-content fast-track and the FR-LST-010 review_flag). A buyer or guest can browse the corkboard board, search with FULLTEXT, filter by category, and open the full-screen listing modal. Categories Service is built here; the admin categories Action moves to Epic 8. The 24-hour listing auto-approval sweep is implemented as a hand-triggered action in this epic; the cron schedule lands in Epic 9.
**FRs covered:** FR-LST-001..017, FR-LND-001..008, FR-ADM-003 (Service only), NFR-PER-002, NFR-PER-003, NFR-PER-006, NFR-SEC-004, AD-7, AD-14

AD-7 inventory rule is enforced at the `Listing\Service` boundary (the only place `quantity_sold` is mutated besides the ticket-creation transaction in Epic 4).

### Epic 4: Purchases, Tickets & Lifecycle
A buyer can confirm a purchase and receive a digital ticket with a TK- code; the seller can redeem the code; the ticket auto-expires after 7 days if not redeemed; either party can file a dispute while active; per-session service handover confirms one session at a time and awards points on the final session. The full ticket state machine (PRD §4.2) is in place. The expiry, 24h listing auto-approve, and 3-day dispute auto-dismiss sweeps are hand-triggered from this epic onward; the cron schedule lands in Epic 9.
**FRs covered:** FR-BUY-001..003, FR-TKT-001..014, NFR-REL-001, NFR-REL-002, NFR-REL-004, NFR-REL-005, NFR-REL-006, NFR-SEC-007, AD-7, AD-8, AD-9
**Implementation notes:** Owns `Ticket/` bounded context. Implements AD-7 (inventory invariant), AD-8 (ticket code format with retry loop), AD-9 (atomic UPDATE pattern for every state-changing operation). The redemption idempotency guarantee is enforced at the Service layer, not by a transaction wrapper.

### Epic 5: Reviews & Ratings
After a ticket is redeemed (within 14 days), both buyer and seller can leave a 1-5 star review with optional text. The seller's public profile shows an aggregated average, a 1..5 distribution, the review count, and the public dispute count (count only, populates only on `dispute_status='upheld'`). Reviews can be inserted only when the ticket is redeemed or expired with no pending dispute (AD-15 gate).
**FRs covered:** FR-RAT-001..005, FR-BUY-003 (entry point), AD-15
**Implementation notes:** Lives in `Ticket/Service/review_service.php`, `Ticket/Model/review_model.php`, and extends `User/View/public_profile.php`. Tightly scoped so the team can ship it as a self-contained PR.

### Epic 6: Points, Ranks & Leaderboards
Every point-earning action writes to an append-only `points_log` (with `UNIQUE uniq_event (event_uuid)`) and updates `users.points` + `users.tier` in the same DB transaction. The new-account 50% multiplier applies only to the first 5 counted transactions and only to counted transactions (not verification, streak, report, or listing). The per-pair daily cap (2 counted transactions per buyer-seller pair) and the velocity check (>300 pts/day or >150 pts/hr → `points_frozen=TRUE` + admin flag) are enforced at insert time. **FRs covered:** FR-PTS-001..010, NFR-PER-005, AD-10

### Epic 7: Reports, Disputes & Moderation Workflow

### Story 1.1: Implement Design Token System

As a developer,
I want consume a single source of truth for every color, typography, spacing, shape, and elevation decision,
So that no surface ships with a one-off hex value, a hard-coded font-size, or a magic spacing value, so visual consistency is enforced at the import.

**FRs/NFRs addressed:** UX-DR-1, UX-DR-2, UX-DR-3

**Acceptance Criteria:**

**Given** a developer imports `public/assets/css/tickettrade.css`
**When** they use `var(--color-primary)`, `var(--color-rank-d)`, `var(--color-status-active-fill)`, etc. as CSS custom properties
**Then** every color in the codebase resolves through the token set in `DESIGN.md` (primary, on-primary, primary-container, on-primary-container, secondary, on-secondary, secondary-container, on-secondary-container, tertiary, on-tertiary, tertiary-container, on-tertiary-container, six tier colors rank-e..rank-s, semantic success/error/warning/info, eight status role fills, light + dark neutral surfaces, corkboard, code surface, WhatsApp, plus AA-pass on-secondary text and darkened status-sold/status-disputed text tokens)
**And** no raw hex value appears in any other CSS file or any inline `style=` attribute

**Given** a developer references a token
**When** they find it documented in the frontmatter of `DESIGN.md`
**Then** the token name and value are listed in the file's `colors`, `typography`, `spacing`, and `shapes` sections
**And** the team can audit the design system by reading one file

**Given** a developer adds a new color or spacing value
**When** they first add the token to the frontmatter of `DESIGN.md` with a name, value, and intent
**Then** the token is then referenced via `var(--...)` in the CSS
**And** no orphan hex values exist; the design system is the single source of truth

**Given** a developer reads the typography section
**When** they see system-ui for body text and Inter for display + headlines
**Then** body text uses `system-ui` per the `typography.body-md` etc. tokens
**And** display + headline sizes use Inter at the documented weights

**Given** a developer needs a monospace surface (ticket code, redemption input, points-log event_uuid)
**When** they use `var(--font-mono)` with `letter-spacing: 0.04em`
**Then** the rendered output matches the spec in `DESIGN.md`
**And** no font is hard-coded in the CSS

**Given** a developer references a spacing value
**When** they use `var(--spacing-1)` through `var(--spacing-6)`
**Then** the value matches the documented scale in `DESIGN.md`
**And** no magic padding/margin numbers in the CSS
