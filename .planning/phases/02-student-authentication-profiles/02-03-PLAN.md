Every later phase adds tabs to this View but the summary header shape is locked here.

    **1. `src/User/Action/public_profile_action.php`:** class `App\User\Action\PublicProfileAction` with `handle()`:
    - The `nickname` path parameter was captured by the Router into `$GLOBALS['_tt_path_params']['nickname']` (per Plan 02-01 Task 1's Router implementation). Read it: `$nickname = $GLOBALS['_tt_path_params']['nickname'] ?? ''; if (!preg_match('/^[A-Za-z0-9_]{3,30}$/', $nickname)) { Support\Error::not_found(); return; }` (the regex matches the Plan 02-02 register's nickname rule; the Router also enforces this regex in its path-param matching).
    - Call `User\Service\user_service::getByNicknameForPublicProfile($nickname)`. The Service filters out `is_banned = TRUE` rows (D-06 — the public profile is hidden for banned users, same as the generic 404) AND re-injects `points` and `is_verified` for the View (see `user_service.php` block above for the rationale). Do NOT call `user_service::getByNickname` here — that returns the strict-sanitized row without `points`, which would render `"0 points"` for every user (T-02 fix).
    - If null, call `Support\Error::not_found()`.
    - Otherwise, render the View: `Support\View::render('User/View/public_profile.php', ['profile' => $profile, 'is_owner' => ($GLOBALS['current_user']['user_id'] ?? null) === (int) $profile['user_id']])`. The `$is_owner` flag lets the View decide whether to show an "Edit profile" button (it's a Phase 2 placeholder; the button is wired in a later phase if/when the design asks for it on the public view). For now, the View is the same for owner and guest.

    **2. `src/User/Service/user_service.php` (Plan 02-02's `getByNickname` stays the real implementation; this plan adds `getByNicknameForPublicProfile`):**
    - `getByNickname(string $nickname): ?array` — Plan 02-02's implementation is unchanged. Looks up the user by case-sensitive `nickname` (matches the URL exactly; D-15). The query: `SELECT * FROM users WHERE nickname = ? AND is_banned = FALSE LIMIT 1`. If no row, return null. Otherwise, strip the sensitive fields via `auth_service::sanitizeUser` (password_hash, is_admin, is_banned, points, points_frozen) and return the row. T-02-10, T-02-20.
    - `getByNicknameForPublicProfile(string $nickname): ?array` — NEW method added by this plan. Re-injects the public-facing fields the View needs (`points`) AFTER `auth_service::sanitizeUser` strips them. The query: `SELECT user_id, nickname, full_name, bio, avatar_id, tier, points, is_verified, created_at FROM users WHERE nickname = ? AND is_banned = FALSE LIMIT 1` (case-sensitive; D-15). If no row, return null. Otherwise, sanitize via `auth_service::sanitizeUser` (which strips `password_hash`, `is_admin`, `is_banned`, `points_frozen`), then explicitly re-add `$row['points'] = (int) $rawRow['points']` and `$row['is_verified'] = (bool) $rawRow['is_verified']` from the SELECT projection (the View needs `points` for the summary header and `is_verified` for the PROF-04 checkmark). The Method exists to resolve the **T-02 points-stripped-by-sanitization** problem: `sanitizeUser` is strict by design (it strips sensitive fields for API responses); the public profile is an explicit exception that needs `points` re-injected. Do NOT modify Plan 02-02's `getByNickname` — both methods coexist; the View only consumes the new method's output. The two methods are NOT aliases: `getByNickname` is for owner-only flows (Plan 02-02's profile-edit, Plan 02-03's possible future authed endpoints); `getByNicknameForPublicProfile` is for the public read view.
    - Why a new method and not a flag on `getByNickname`: the strict-by-default `sanitizeUser` is the security posture; loosening it in one place would erode T-02-10 / T-02-20 / T-02-27. A dedicated public-profile method makes the exception explicit and testable.
    - `getPublicProfile(string $nickname): ?array` — alias for `getByNicknameForPublicProfile` (preserved for Plan 02-02 callers that may already reference it; same return shape).
