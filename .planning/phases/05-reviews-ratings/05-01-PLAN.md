# Plan 05-01: Reviews Service + Actions

## Context

Phase 5 closes the trust loop. After a ticket reaches a terminal state (`redeemed` or `expired`) with `dispute_status='none'`, both buyer and seller can leave a 1-5 star review with optional text within a 14-day window. This plan (tracer) ships the WRITE path end-to-end: schema → service → action → view → JS widget. Plan 05-02 ships the READ path (profile aggregation + listing modal row).

Honors CONTEXT.md decisions:
- **D-01** star input is a fieldset of 5 named radios with hidden inputs, 24px icons, visually-hidden legend.
- **D-02** RAT-04 (seller rates buyer) writes a `reviewer_role='seller'` row; not surfaced on profile in Phase 5.
- **D-03** "Leave review" button renders only on `/purchases` rows where `redeemed_at` is within 14 days.
- **D-04** no GET route for the form; modal-launched only.
- **D-05** `points_service::awardReviewPoints()` is sole writer of the review-side `points_log` row.
- **D-06** points award runs inside the same DB transaction as the `reviews` INSERT.
- **D-08** review list pagination deferred to Plan 05-02.

<action>
Add `awardReviewPoints(int $revieweeId, int $reviewerId, int $ticketId, int $commentLength): array` to `src/Points/Service/points_service.php`. The method is a near-clone of `awardTransaction`'s discipline:
1. Read `users.redeemed_count` + `points_frozen` for the reviewee (lock with `SELECT ... FOR UPDATE`).
2. Honor `points_frozen=TRUE` → return `ok=true, data.skipped='points_frozen'` (no row written).
3. If `commentLength < 50` → return `ok=true, data.skipped='no_points'` (no row written).
4. Apply FR-PTS-007 halving: effective delta = `redeemed_count < 5 ? floor(10 * 0.5) : 10`.
5. Insert ONE `points_log` row with `reference_type='review'`, `reference_id=$ticketId`, distinct UUID v7 `event_uuid`, `delta=$effectiveDelta`, `balance_after=$newPoints`, `metadata_json='{"comment_length":$commentLength,"reviewer_id":$reviewerId}'`.
6. UPDATE `users.points`, `users.tier`, `redeemed_count = redeemed_count + 1` for the reviewee only.
7. Participate in the outer transaction — do NOT call `commit()` or `rollBack()` (the caller owns the transaction boundary). If no outer transaction is active, this method opens one and commits on success.
8. Return `ok=true, data.delta, data.event_uuid`; on failure return `ok=false, error.code='E_POINTS_WRITE'`.
9. The reviewer gets NO points (no row, no UPDATE) — the parameter is for audit/trace only.
</action>

## Risks

- **Schema ENUM ordering** — `reviewer_role ENUM('buyer','seller')` order must match the UNIQUE key column. Migration is `017`; the Phase 4 schema uses `dispute_status ENUM('none','pending','rejected','upheld')` — same MySQL ENUM-style. No collision.
- **Points service growth** — `awardReviewPoints` is a near-clone of `awardTransaction`. If Phase 6 generalizes points (velocity cap, pair cap), both methods will be refactored together. Acceptable WAD-scoped duplication; the alternative is a deeper abstraction with no current second caller.
- **Modal-per-row DOM bloat** — One modal per redeemed ticket row. At ≤50 tickets on `/purchases` (Phase 3 cap), the DOM weight is acceptable for WAD scope.
- **Cross-context `submitReview` calls `awardReviewPoints`** — Two Services collaborate inside one transaction. Phase 4's `redeemTicket` does the same (`ticket_service` calls `points_service`); the pattern is established.
